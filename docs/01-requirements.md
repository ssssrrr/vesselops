## 1. 배경 및 목적

선박용 대형 엔진은 항해 중 육상 지원을 받을 수 없어, **고장이 곧 운항 중단(off-hire)** 으로 직결된다.
기관 상태를 육상에서 연속 감시하고 이상 징후를 조기에 포착하면,
계획 정비(Planned Maintenance) → **상태기반 정비(CBM, Condition Based Maintenance)** 로 전환할 수 있다.

본 프로젝트는 선박에 탑재된 기관의 운전 데이터를 수집·전송·저장·분석하여
육상 관제에서 선단(Fleet) 단위로 감시하는 플랫폼을 구축하는 것을 목적으로 한다.

### 1.1 해결하려는 문제

| 문제 | 현행 | 목표 |
|---|---|---|
| 기관 상태 파악 | 본선 기관일지 수기 작성, 입항 후 취합 | 육상에서 실시간 확인 |
| 이상 감지 | 경보 발생 후 사후 대응 | 추세 이탈 단계에서 사전 경고 |
| 선단 비교 | 선박별 개별 관리 | 동형선 간 성능 비교 |
| 정비 시점 | 운전시간 기준 일률 정비 | 상태 기반 정비 시점 산출 |

## 2. 범위

### 2.1 포함 범위 (In Scope)
- **본선 Edge 수집기 개발** — 기관 자동화 시스템(AMS)에서 OPC UA로 계측값 수집
- 본선 Edge 수집기 ↔ 육상 플랫폼 간 텔레메트리 전송 (MQTT over TLS)
- 시계열 데이터 저장 및 다운샘플링 보존 정책
- 선박·기관·계측점(Tag) 마스터 관리
- 임계값·편차 기반 알람 룰 엔진 및 알람 이력 관리
- 실시간 대시보드 (선단 현황 / 선박 상세 / 기관 상세)
- 성능지표 산출 (SFOC, 과급기 효율, 실린더 배기온도 편차)
- 사용자 인증·권한 (육상 관제 / 본선 기관사 / 관리자)
- 클라우드 배포 및 CI/CD

### 2.2 제외 범위 (Out of Scope)
- 실제 선박 통신위성(VSAT/Iridium) 연동 — 대역 제약만 설계에 반영
- 기관 제어(Write) 기능 — **감시 전용(Read-only)**. 안전상 원격 제어는 제외
- 선급(Class) 인증 대상 기능
- 실 계측 데이터 — 실선 AMS 대신 **OPC UA 서버로 동작하는 시뮬레이터**를 사용한다.
  다만 **인터페이스 규격(OPC UA NodeId 체계, 데이터타입, 품질코드)은 실제와 동일**하게 맞추어,
  실선 적용 시 엔드포인트 주소 변경만으로 대체 가능하도록 한다.

> 원격 제어를 제외한 것은 의도적 설계 결정이다. 기관 제어는 선급 규정과 SOLAS 적용 대상이며,
> 감시계와 제어계를 물리적으로 분리하는 것이 선박 시스템의 기본 원칙이다.
> Edge 수집기는 OPC UA 세션을 **읽기 전용 권한**으로만 생성한다(FR-107).

### 3.1 기술 스택 및 선정 근거

| 구성요소 | 기술 | 선정 근거 |
|---|---|---|
| 시뮬레이터 (AMS 대체) | **Node.js 22 + node-opcua** | 실선 AMS 자리에 들어가는 대역물. **OPC UA 서버로 동작**시켜 인터페이스 규격을 실제와 동일하게 유지 |
| Edge 수집기 (본선) | **Node.js 22 + node-opcua** | OPC UA 클라이언트. 구독 처리와 버퍼 큐 모두 I/O 중심 작업이라 이벤트 루프가 적합 |
| Ingest Gateway | **Node.js 22** | 다수 선박의 동시 연결을 I/O 바운드로 처리. 이벤트 루프가 고빈도·소용량 텔레메트리 수신에 적합 |
| 업무 API | **Java 21 / Spring Boot 3.5** | 알람 룰·상태 전이·이력 등 업무 로직. 정적 타입과 단위 테스트로 규칙을 고정한다. DB 접근은 `JdbcClient` (`02-architecture.md` ADR-008) |
| DB | **PostgreSQL 16 + TimescaleDB** | 시계열(hypertable)과 관계형 마스터를 한 DB에서 처리. 별도 TSDB 도입 대비 운영 복잡도 감소 |
| 메시징 | **MQTT (Mosquitto)** | 선박-육상 저대역·간헐 단절 환경 표준 프로토콜. QoS 1과 세션 유지로 재전송 보장 |
| 배포 | **Docker Compose / AWS EC2** | 단일 VM에서 전체 스택 재현. 개발-운영 환경 동일성 확보 |

> **Node.js와 Java를 함께 쓰는 이유**: 수집 계층은 연결 수와 처리량이 지배하는 I/O 문제이고,
> 업무 계층은 도메인 복잡도와 트랜잭션 정합성이 지배하는 문제다. 성격이 다르므로 분리했다.
> 두 서비스는 DB와 내부 REST로만 통신하여 독립 배포가 가능하다.

## 4. 기능 요구사항

### 4.1 본선 데이터 수집 — OPC UA 구간 (FR-100)

본선 기관 자동화 시스템(AMS)과 Edge 수집기 사이 구간. 선내 유선 LAN 이므로 대역 제약이 없다.

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-101 | AMS의 OPC UA 서버에 접속하여 세션 유지. 단절 시 지수 백오프로 자동 재접속 | 필수 |
| FR-102 | 태그맵에 정의된 NodeId 를 구독(Subscription). 미지원 서버는 주기 폴링으로 대체 | 필수 |
| FR-103 | **Deadband 필터** — 직전 전송값 대비 변화량이 태그별 임계 미만이면 전송 생략. 단 무전송이 heartbeat 간격을 넘으면 강제 전송 | 필수 |
| FR-104 | **로컬 버퍼링** — 육상 통신 단절 시 디스크 큐에 적재, 복구되면 시간순 재전송 | 필수 |
| FR-105 | OPC UA StatusCode 를 품질코드로 변환·보존 (Good / Uncertain / Bad) | 중요 |
| FR-106 | 수집분을 MQTT 로 발행 (QoS 1, TLS, 배치 묶음) | 필수 |
| FR-107 | **읽기 전용 강제** — Write 및 Method 호출 금지. 세션 권한 자체를 읽기로 제한 | 필수 |
| FR-108 | **적응형 전송** — 평상시 1분 요약 전송, 이상 징후 감지 시 1초 원본 전송으로 자동 전환 | 필수 |
| FR-109 | **Pre-trigger 링버퍼** — 전송 모드와 무관하게 1초 원본을 로컬에 10분간 보관하고, 트리거 발생 시 직전 구간을 소급 전송 | 필수 |
| FR-110 | **송신 우선순위 큐** — P0(알람) > P1(고해상도·소급분) > P2(정기 요약) 순으로 전송 | 필수 |

> **FR-103·104·108·109 가 위성통신 환경 설계의 핵심이다.**
> 본선에서는 1초 주기로 수집하되 육상으로는 걸러서 보내고(대역·비용, NFR-07),
> 끊기면 쌓아뒀다 복구 시 채우며(가용성), 평상시에는 요약만 보내되
> 이상 시에는 이상 발생 **이전 구간까지** 원본으로 확보한다(진단 가능성).

#### 4.1.1 적응형 전송 상세 (FR-108 ~ FR-110)

**해결하려는 문제**
정상 운전 중 1초 해상도를 계속 전송하는 것은 대역 낭비다. 그러나 단순히 전송 주기를 낮추면
정작 고장 진단에 필요한 **이상 발생 직전 구간의 해상도를 잃는다.**

**설계 원칙 — 전환 속도에 의존하지 않는다**

| 구분 | 내용 |
|---|---|
| 판정 주체 | **Edge 수집기**. 육상이 판단하면 왕복 지연만큼 늦고, 요약 데이터만으로는 조기 감지가 어렵다 |
| 전환 기준 | 육상 알람 기준보다 **낮게** 설정 (예: 편차 알람 50℃ → Edge 전환 30℃). 오탐을 허용하고 지연을 줄인다 |
| **소급 확보** | 트리거와 무관하게 1초 원본을 항상 링버퍼에 보관. 트리거 시 **직전 10분을 소급 전송**한다 |
| 요약의 정보량 | 요약 전송 시 평균만이 아니라 **min·max·표준편차·표본수**를 함께 담아 순간 스파이크를 잃지 않는다 |
| 알람 전송 | 모드와 무관하게 **항상 즉시** 별도 토픽으로 전송 |

**Edge 측 전환 트리거 조건**

| 조건 | 기준 |
|---|---|
| 임계값 근접 | 경보 설정값의 80% 도달 |
| 편차 확대 | 실린더 간 편차가 알람 기준의 60% 도달 |
| 변화율 초과 | 단위시간당 변화량이 기준 초과 |
| 품질 저하 | Bad/Uncertain 품질이 연속 발생 |
| 복귀 | 모든 조건 해소 후 정상 10분 지속 |

**보장 범위의 한계**
통신 단절 중에는 전송 자체가 불가능하므로 NFR-08·NFR-10 은 **통신 가용 시**에 한해 적용한다.
단절 중에는 버퍼에 적재하고, 복구 시 우선순위 큐 순서(P0→P1→P2)로 전송한다.

### 4.4 알람 (FR-300)

| ID | 요구사항 | 우선순위 |
|---|---|---|
| FR-301 | 임계값 알람 — HI/HIHI/LO/LOLO 4단계 | 필수 |
| FR-302 | **편차 알람** — 실린더별 배기온도가 전 실린더 평균 대비 ±X℃ 이탈 | 필수 |
| FR-303 | 변화율 알람 — 단위시간당 변화량 초과 (예: 베어링 온도 급상승) | 중요 |
| FR-304 | 채터링 방지 — 지속시간(dwell) 조건 충족 시에만 알람 확정 | 필수 |
| FR-305 | 알람 확인(Acknowledge) 및 해제 이력 관리 | 필수 |
| FR-306 | 알람 발생 시 등록된 담당자에게 통지 | 선택 |

> **FR-302가 이 시스템의 핵심 가치다.** 실린더 배기온도는 절대값이 정상 범위여도
> 실린더 간 편차가 벌어지면 연료분사밸브 불량·배기밸브 누설의 조기 징후다.
> 단순 임계값 감시로는 잡을 수 없는, 도메인 지식이 필요한 진단이다.

### 4.5 성능 분석 (FR-400)

| ID | 요구사항 | 우선순위 |
|---|---|---|

## 5. 비기능 요구사항

| ID | 항목 | 목표 |
|---|---|---|
| NFR-01 | 수집 처리량 | 4척 × 약 36태그 × 1초 주기 ≈ **142 값/초** 무손실 (선단 확장 시 10척까지 여유) |
| NFR-02 | 대시보드 반영 지연 | 수신 → 화면 표시 1초 이내 |
| NFR-03 | 조회 응답 | 24시간 트렌드 조회 500ms 이내 (다운샘플링 적용) |
| NFR-04 | 데이터 보존 | 원본 30일 / 1분 평균 1년 / 1시간 평균 5년 |
| NFR-05 | 통신 보안 | MQTT TLS, HTTPS(Let's Encrypt), 평문 전송 금지 |
| NFR-06 | 가용성 | 컨테이너 자동 재시작, DB 일 1회 백업 |
| NFR-07 | **통신 데이터량** | **선박당 월 1.5 GB 이하** (평균 약 4.6 kbps). 해상 통신 요금제가 월 데이터량 기준으로 판매되므로 전송률이 아닌 데이터량으로 정의한다 |
| NFR-08 | 고해상도 전환 도착 | 트리거 발생 → 첫 1초 원본의 육상 DB 도착까지 **15초 이내** *(통신 가용 시)* |
| NFR-09 | Pre-trigger 확보 | 트리거 시점 기준 **직전 10분** 1초 원본 **결측 0건** |
| NFR-10 | 알람 전송 지연 | 알람 발생 → 육상 수신까지 **3초 이내** *(통신 가용 시)* |
| NFR-11 | 모드 전환 판정 | 조건 충족 → Edge 전환 결정까지 **5초 이내** |

> **NFR-07 산정 근거**
>
> | 구분 | 전송률 | 월 데이터량/척 |
> |---|---|---|
> | 필터 없음 (142값/초 × 약 65 byte) | 약 74 kbps | 24 GB |
> | Deadband 만 적용 | 약 15 kbps | 약 5 GB |
> | **Deadband + 적응형 전송 + 압축** | **약 4.6 kbps** | **약 1.5 GB** |
>
> 실측치는 `08-test.md` 에 기록한다.
